askwire 笔记 · 2026-10-25 · English

decline 还是 cancel，到底是谁在回答

仅在 Linux 上实测。macOS 只跑了单元测试，Windows 未测试。

MCP elicitation 让服务器在工具调用中途停下来问用户一个问题。回复里只有三个词之一：accept、decline、cancel。我们让 Claude Code、Codex 和 opencode 对着一个探针服务器跑了一遍，看看回来的是哪个词、有多快，以及到底有没有人可能看到这个问题。

Q1

规范怎么说

MCP 规范为 elicitation/create 定义了三种响应：

  • accept：用户明确同意并提交，content 中带有数据。
  • decline：用户明确拒绝了请求。
  • cancel：用户没有做出明确选择就关掉了（关闭对话框、按 Esc）。

三者都被描述为“用户做了什么”，没有一个表示“根本没有用户”。本文讲的就是这个空档。

Q2

实际回来了什么

2026-10-25 的最新版本，一台 Linux 机器。每次运行的答案都相同，毫秒数因机器而异。

多次运行中：claude -p 在 3–5 ms 内回答 cancel，codex exec 在 1–3 ms 内回答 decline。两者都没有画出任何界面，因为根本没有终端可画。

在交互式 TUI 里，问题确实被画出来了（askwire 在 120–230 ms 后在屏幕上看到了探针的 nonce），然后 askwire 按下 Esc。Claude Code 两次都返回 cancel；Codex 对 form 返回 cancel，对 URL 请求返回 decline。按规范，未做选择就关掉应该是 cancel。

opencode 1.19.4 不声明 elicitation 能力（capabilities 为 {roots:{}}），所以 SDK 拒绝发送。强行发送原始 elicitation/create 会得到 -32601 Method not found。这是诚实的回答。

Q3

到底是谁在回答

三点观察，每一点都有探针日志为证：

  • 无头模式下的 decline 不是人在说不。codex exec（审批策略 never）在几毫秒内返回 decline，而这是规范留给“明确拒绝”的词。
  • 有没有人，cancel 看起来都一样。无人的 claude -p 和真按了 Esc 的 Claude Code TUI 发回的回复完全相同。服务器无法区分“被关掉了”和“根本没人”。
  • accept 也证明不了有人。在 claude -p 下，一个返回 accept 的 Claude Code Elicitation hook 约 20 ms 就给出 {"action":"accept","content":{"confirm":true}}。hook 的输入包含服务器名、消息、模式和请求的 schema，脚本可以回答任何问题。

如果回复在 3 ms 内就回来了，那就没有人读过这个问题。

Q4

测量是怎么做的

  • 探针服务器。一个 stdio MCP 服务器，每个工具只发一次 elicitation/create（form、url，以及对未声明该能力的客户端发一次原始请求），并带上每次运行的 nonce，例如 AW-4FJ7。它记录客户端在 initialize 时声明的能力、回答、往返耗时以及任何 JSON-RPC 错误。
  • 本地替身模型。一个小端点，能说 Anthropic Messages、OpenAI Responses 和 Chat Completions 格式，刚好够调用下一个探针工具然后结束。不需要账号、API key，也不消耗 token。
  • 一次性 home 目录。每个客户端都在临时的 HOME / CODEX_HOME / XDG 目录里运行，通过其文档中的自定义端点配置指向替身模型。你自己的配置不会被读取或修改。
  • 屏幕检查。使用 --tui 时，真实的交互式客户端运行在私有 tmux 服务器中。askwire 等待 nonce 出现在屏幕上，记录时间，然后按 Esc。
npx github:Blackman99/askwire            # 无头：claude -p、codex exec、opencode run
npx github:Blackman99/askwire --tui      # tmux 中的真实 TUI（需要 tmux）

Q5

你的服务器应该怎么做

  1. 只把带有你所要求内容的 accept 视为同意。
  2. decline 和 cancel 同等对待：不继续执行。各客户端对二者的用法并不一致。
  3. 给请求加超时，没有回答就当作“不”。
  4. 客户端以无头模式运行时，直接拒绝高风险操作而不是去问。如果操作很重要，记录它被 accept 的事实；hook 也能 accept。
const r = await server.server.elicitInput({
  message: "Delete 312 rows from orders?",
  requestedSchema: { type: "object", properties: { confirm: { type: "boolean" } }, required: ["confirm"] },
}, { timeout: 60_000 });                       // no answer in 60 s: treated as no

if (r.action !== "accept" || r.content?.confirm !== true) {
  // decline and cancel both land here: they mean the same thing to you
  return { content: [{ type: "text", text: "Not confirmed. Nothing was changed." }] };
}
log.info("confirmed via elicitation", { client: server.server.getClientVersion()?.name });  // accept can come from a hook

Q6

没有测到的部分

以上所有结果仅在 Linux 上实测。单元测试也在 macOS 上运行，但尚未在 macOS 上做过真实客户端测试。Windows 未测试。Cursor agent、Gemini CLI、Copilot CLI 和 Kiro CLI 尚未覆盖，Streamable HTTP 和 MCP Tasks 内的 elicitation 也未覆盖。
